# 攻花 H5 项目发布上线阶段步骤

## 1. 文档目标

- 本文档用于规划攻花 H5 从本地开发走向测试、灰度、正式上线和后续运营的完整工作。
- 开发阶段状态参考 `docs/step/开发阶段step.md`。
- 画面体验工作参考 `docs/step/画面优化step.md`。
- 功能结构和联机能力工作参考 `docs/step/功能优化step.md`。
- 上线前必须遵守根目录 `AGENTS.md`，不得在代码、日志或文档中暴露密钥、token、私钥或 `.env` 真实值。

## 2. 阶段 1：上线方式选择

目标：明确当前项目适合的部署模式，并为后续联机能力预留升级路径。

可选上线方式：

- 静态前端 + 独立 Node 服务：
    - 前端 `apps/web` 构建后部署到静态站点服务。
    - 后端 `apps/server` 独立部署为 Node 服务。
    - 适合当前前后端分离结构，推荐作为首版上线方式。
- 单机演示包：
    - 本地或内网运行前端和后端。
    - 适合规则验收、亲友测试和早期体验验证。
    - 不适合作为正式公开渠道。
- 容器化部署：
    - 前端构建产物和后端服务分别打 Docker 镜像。
    - 适合云服务器、Kubernetes 或后续多环境发布。
- 平台托管：
    - 前端可部署到 Vercel、Netlify、Cloudflare Pages 或对象存储 CDN。
    - 后端可部署到 Render、Railway、Fly.io、云服务器或国内云厂商。
    - 若接 WebSocket，需要确认平台是否支持长连接和连接时长限制。

推荐首版：

- 前端：静态构建 + CDN。
- 后端：Node 服务 + 进程守护。
- 数据：首版可继续内存状态用于测试；正式联机前必须接持久化存储。

完成标准：

- 明确测试环境和正式环境的部署方式。
- 明确前端访问后端 API 的环境变量配置。
- 明确是否支持 WebSocket、HTTPS、自定义域名和日志采集。

## 3. 阶段 2：发布渠道规划

目标：明确用户从哪里进入游戏，以及不同渠道需要的适配工作。

渠道：

- Web 浏览器：
    - PC 浏览器。
    - 移动端浏览器。
    - 平板浏览器。
- H5 分享链接：
    - 微信、QQ、飞书、浏览器分享。
    - 需要处理横屏提示、加载性能和分享标题。
- 内测渠道：
    - 固定测试链接。
    - 测试群发布。
    - 反馈表单或问题收集文档。
- 后续可选渠道：
    - PWA 桌面图标。
    - 小程序包装。
    - App WebView 包装。

渠道准备事项：

- 配置正式域名和 HTTPS。
- 配置分享标题、描述和图标。
- 配置移动端 viewport、横屏适配和安全区域。
- 配置错误页面和对局不存在回首页。
- 准备用户反馈入口。

完成标准：

- 测试用户可以通过固定链接进入游戏。
- 移动端打开后核心对局功能可用。
- 分享入口不会暴露测试环境地址或内部路径。

## 4. 阶段 3：代码实现准备

目标：补齐上线所需的配置、构建、环境隔离和稳定性能力。

任务：

- 环境变量：
    - `VITE_API_BASE_URL`：前端请求后端地址。
    - `SERVER_PORT`：后端服务端口。
    - `NODE_ENV`：运行环境。
    - 后续 AI 能力使用 `OPENAI_API_KEY` 等密钥，但必须只放在服务端环境变量中。
- 构建脚本：
    - 前端构建脚本。
    - 后端构建脚本。
    - 全量检查脚本。
    - 部署前检查脚本。
- 健康检查：
    - 后端 `/health`。
    - 前端静态资源可访问检查。
    - API 连通性检查。
- 错误处理：
    - 对局不存在回首页。
    - 后端接口统一错误响应。
    - 前端请求空响应和 JSON 解析失败兜底。
- 日志：
    - 前端控制台中文日志。
    - 后端终端中文日志。
    - 生产环境日志级别控制。
    - 禁止输出密钥、token、完整环境变量。
- 版本信息：
    - 构建版本号。
    - 发布时间。
    - Git commit 或构建标识。
    - 前端页面可选显示版本信息。
- 数据准备：
    - 正式联机前接入数据库。
    - 单机测试环境可继续使用内存仓库。
    - 定义对局过期清理策略。

完成标准：

- `pnpm run lint`、`pnpm run typecheck`、`pnpm run test`、`pnpm run build` 上线前全部通过。
- 前端构建产物能通过静态服务器访问。
- 后端能在生产模式启动并响应健康检查。
- 环境变量缺失时有明确错误提示。

## 5. 阶段 4：部署流程

目标：形成可重复、可回滚、可检查的发布流程。

流程：

1. 合并发布分支前完成代码审查。
2. 执行本地或 CI 检查：
    - `pnpm exec prettier --check .`
    - `pnpm run lint`
    - `pnpm run typecheck`
    - `pnpm run test`
    - `pnpm run build`
3. 生成构建产物。
4. 部署后端服务。
5. 部署前端静态资源。
6. 配置域名、HTTPS 和反向代理。
7. 执行线上冒烟测试。
8. 发布内测公告或正式公告。
9. 观察日志、错误和用户反馈。

回滚方案：

- 保留上一个稳定前端构建产物。
- 保留上一个稳定后端版本。
- 数据库变更必须有回滚脚本或兼容策略。
- 如果新版本影响创建对局或提交动作，优先回滚后端。

完成标准：

- 任一环境可以按同一流程重复部署。
- 发布失败时可以明确回滚到上一版本。
- 发布后有可执行的冒烟检查清单。

## 6. 阶段 5：线上验证与监控

目标：发布后及时发现问题，保证核心对局流程可用。

验证清单：

- 首页可打开。
- 快速开始可创建对局。
- 对局页可查询状态。
- 真人可以出攻牌、守牌、停攻、放弃防守和确认收牌。
- 机器人可以按 0.5 秒延迟推进动作。
- 事件栏正常显示最新事件。
- 牌堆耗尽后只出不添和排名正常。
- 对局不存在会自动回首页。
- 移动横屏下核心元素不遮挡。

监控指标：

- 前端静态资源加载失败率。
- API 请求成功率。
- 创建对局失败率。
- 提交动作失败率。
- 机器人推进失败率。
- 后端进程重启次数。
- 服务响应耗时。
- 用户反馈问题数量。

完成标准：

- 发布后能判断系统是否正常。
- 核心故障有日志可查。
- 用户反馈能对应到版本和时间。

## 7. 阶段 6：运营工作

目标：让上线后的用户体验、反馈收集和版本迭代形成闭环。

任务：

- 准备游戏说明：
    - 基础规则。
    - 出牌方式。
    - 防守方式。
    - 停止进攻。
    - 放弃防守。
    - 只出不添和排名。
- 准备新手引导：
    - 首次进入提示。
    - 拖拽出牌提示。
    - 机器人手牌说明。
    - 事件栏说明。
- 准备反馈渠道：
    - 问题反馈表。
    - 测试群。
    - 版本问题记录文档。
- 准备版本公告：
    - 新增能力。
    - 修复问题。
    - 已知问题。
    - 下一步计划。
- 准备运营数据：
    - 访问人数。
    - 创建对局数。
    - 完成对局数。
    - 平均对局时长。
    - 中途退出比例。
    - 常见错误类型。
- 准备内容更新：
    - 规则解释页面。
    - 常见问题。
    - 更新日志。
    - 内测名单或反馈贡献记录。

完成标准：

- 用户遇到问题有反馈入口。
- 发布后能收集关键体验数据。
- 每次版本更新有清晰说明和已知问题列表。

## 8. 阶段 7：合规与安全

目标：避免上线过程中出现隐私、密钥和数据安全风险。

任务：

- 不在前端代码中写入任何服务端密钥。
- 不在日志中输出 token、私钥、完整环境变量或用户敏感数据。
- 如果接入用户系统，需要明确收集哪些用户信息。
- 如果接入运营统计，需要明确统计字段和用途。
- 对房间号、玩家身份、动作提交做基础校验，避免越权操作。
- 对生产接口开启 CORS 白名单，不允许任意来源访问正式服务。
- 对接口增加基础限流，避免恶意创建大量对局。

完成标准：

- 密钥只存在于服务端环境变量或部署平台密钥管理中。
- 线上日志不包含敏感信息。
- 对外接口有基本的参数校验、来源控制和限流策略。

## 9. 发布前最终检查

必须完成：

- 开发阶段核心能力已实现。
- 画面优化阶段至少完成当前目标渠道需要的适配。
- 功能优化阶段中与上线强相关的稳定性工作已完成。
- `docs/rules.md`、阶段文档和代码行为没有明显冲突。
- 上线环境变量已配置。
- 域名和 HTTPS 已配置。
- 冒烟测试通过。
- 回滚方案可执行。
