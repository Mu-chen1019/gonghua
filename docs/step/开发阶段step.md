# 攻花 H5 项目开发阶段步骤

## 1. 文档目标

- **阶段状态：已实现。**
- 本文档用于指导当前 TypeScript + React + Node 版攻花 H5 项目的后续开发。
- 当前项目采用 monorepo 结构，前端、后端、共享协议和游戏核心规则分包维护。
- 规则基准优先参考 `docs/rules.md`；当前首版范围摘要参考 `docs/规则基准.md`。
- 后续开发默认遵守根目录 `AGENTS.md`，包括注释、格式化、测试、文档沉淀和改动范围控制要求。
- 本文档覆盖阶段 1-11 的核心单机开发闭环；后续画面、功能和发布上线工作分别维护在独立 step 文档中。

## 2. 当前项目结构

```text
gonghua/
├─ apps/
│  ├─ web/                 # React H5 前端
│  │  └─ src/
│  │     ├─ app/           # 路由与应用外壳
│  │     ├─ components/    # 前端可复用组件
│  │     ├─ pages/         # 页面级视图
│  │     ├─ services/      # 请求封装
│  │     ├─ stores/        # UI 状态
│  │     └─ styles.css     # 全局样式
│  └─ server/              # Node/Fastify 后端
│     └─ src/
│        ├─ routes/        # HTTP 路由
│        ├─ app.ts         # Fastify 应用创建
│        ├─ gameStore.ts   # 服务端内存对局状态
│        └─ logger.ts      # 服务端日志
├─ packages/
│  ├─ contracts/           # 前后端共享协议、DTO、枚举
│  └─ game-core/           # 游戏规则、状态机、纯逻辑测试
└─ docs/                   # 规则、阶段、模块方案文档
```

## 3. 分层原则

### 3.1 前端 `apps/web`

- 只负责页面、交互、动画和玩家可见视角展示。
- 不保存完整对局状态，不直接实现游戏规则判断。
- 通过 `apps/web/src/services/api.ts` 与后端通信。
- 页面新增复杂能力时，优先拆到 `components`、`services`、`stores`，避免页面文件膨胀。

### 3.2 后端 `apps/server`

- 保存完整对局状态，是动作提交和规则校验的权威入口。
- HTTP 路由只做参数校验、调用状态层、包装响应，不直接写复杂规则。
- 服务端状态管理集中在 `apps/server/src/gameStore.ts`。
- 服务端日志优先通过 `apps/server/src/logger.ts` 输出。

### 3.3 协议 `packages/contracts`

- 前后端共享的请求、响应、DTO、枚举和错误码必须在这里定义。
- 新增接口字段前，必须先确认字段来源和类型，不允许前端或后端单边造字段。
- UI 临时字段不能混入协议类型；提交前必须转换为协议字段。

### 3.4 游戏核心 `packages/game-core`

- 负责牌堆、发牌、翻主牌、首攻、攻防、收牌、添牌、轮转、结算等纯逻辑。
- 不依赖 React、Fastify、浏览器 API、数据库或外部运行环境。
- 行为变化必须优先补 `packages/game-core/test`。

## 5. 推荐开发阶段

> 以下阶段 1-10 均已实现，保留明细用于回溯核心单机版能力边界和验收标准。

### 阶段 1：规则与文档基准整理

目标：确保规则口径、当前首版范围和开发步骤一致。

任务：

- 明确 `docs/rules.md` 是完整规则基准。
- 明确 `docs/规则基准.md` 是当前首版范围摘要。
- 清理文档中旧项目路径、旧技术栈和不存在文件引用。
- 补充后续阶段的边界和验收标准。

完成标准：

- 文档之间不再出现明显冲突。
- 任一规则改动都有明确来源和落点。

### 阶段 2：项目骨架与协议基础

目标：建立前端、后端、共享协议和游戏核心的基本结构。

任务：

- 搭建 `apps/web`、`apps/server`、`packages/contracts`、`packages/game-core`。
- 建立基础路由、页面骨架、请求封装和后端健康检查。
- 定义基础 DTO、枚举、错误码和响应结构。
- 建立格式化、lint、typecheck、test 脚本。

完成标准：

- 前端可以启动页面。
- 后端可以响应健康检查。
- 前后端可以共享 `packages/contracts` 类型。
- `pnpm run lint`、`pnpm run typecheck`、`pnpm run test` 可执行。

### 阶段 3：开局状态生成

目标：完成合法对局初始状态。

任务：

- 生成 54 张标准扑克牌，包含大小王。
- 为每张牌生成唯一 `id`。
- 实现可注入 seed 的洗牌逻辑。
- 默认 4 人发牌，当前单副牌玩法支持 2-6 人，更多人数需要后续多副牌或发牌规则扩展。
- 每名玩家初始发 8 张。
- 翻主牌，若翻到大小王则放回、重洗、重翻。
- 将最终普通主牌放回牌堆底部，并保持其属于 `deck`。
- 标记主花色和主牌展示状态。
- 校验牌数守恒和状态归属唯一性。

完成标准：

- 创建对局后得到合法初始局面。
- 主牌不是大小王。
- `trumpCard` 仍存在于 `deck` 中。
- 总牌数始终为 54。

测试重点：

- 发牌数量正确。
- 牌堆底部主牌归属正确。
- 固定 seed 下结果可复现。
- 翻到大小王时不会丢牌。

### 阶段 4：首攻判定与玩家视角

目标：确定第一轮主攻、受攻、助攻和当前行动人。

任务：

- 按最小普通主花色牌确定首攻。
- 无普通主花色牌时，依次按小王、大王、随机合法玩家确定首攻。
- 根据座位顺时针关系计算受攻方和助攻方。
- 初始化 `currentTurnSeat`。
- 后端基于完整状态生成玩家可见视角。
- 非当前玩家的手牌只返回数量，不返回具体牌面。

完成标准：

- 任意合法开局都能确定第一轮角色关系。
- 前端展示的数据来自服务端玩家视角，不读取完整对局状态。
- 座位计算不写死 4 人。

测试重点：

- 有主花色牌时最小主牌先攻。
- 无普通主花色牌时按大小王和随机规则兜底。
- 玩家视角过滤不会泄漏其他玩家手牌。

### 阶段 5：基础攻防动作

目标：让一轮内的基础攻防可以通过统一动作入口推进。

任务：

- 实现 `PLAY_ATTACK_CARD`。
- 实现 `PLAY_DEFENSE_CARD`。
- 实现同点加攻校验。
- 实现大小王作为守牌触发封攻。
- 实现守牌撤回。
- 实现守牌移动/换位。
- 实现主攻方和助攻方停止进攻。
- 实现放弃防守。
- 实现受攻失败后的 `DEFENSE_COLLECTING` 收牌追加阶段。
- 实现受攻方确认收牌并把桌面全部牌收入手牌。
- 实现受攻方空手且仍有未防住牌时进入 `WAITING_DEFENSE_REFILL`。
- 前端操作区接入所有当前阶段支持的动作。

完成标准：

- 一轮可以从 `FIRST_ATTACK_READY` 推进到 `ROUND_ACTIVE`。
- 合法防守全部完成后，如果主攻方和所有助攻方尚未停止进攻，仍保持 `ROUND_ACTIVE`。
- 合法防守全部完成，且主攻方和所有助攻方均停止进攻后进入 `ROUND_RESULT_READY`。
- 放弃防守后进入 `DEFENSE_COLLECTING` 且结果为受攻失败。
- `DEFENSE_COLLECTING` 阶段攻击方可以继续追加合法攻牌。
- 受攻方确认收牌后，桌面全部攻守牌进入受攻方手牌，并进入 `ROUND_RESULT_READY`。
- 封攻后只允许另一张大小王作为特殊追加攻牌。
- 守牌撤回和换位后仍保持牌数守恒。

测试重点：

- 非法角色不能出牌。
- 防守牌必须能合法压制对应攻牌。
- 同点加攻必须命中桌面已有牌点数。
- 攻击方打出大小王不触发封攻。
- 防守方打出大小王触发封攻。
- 防守方防住全部攻牌后，攻击方仍可根据桌面守牌继续追加合法攻牌。
- 主攻方和所有助攻方停止进攻后，才形成受攻成功结果。
- 守牌撤回后回到受攻方手牌。
- 守牌换位后所有守牌仍能压制对应攻牌。
- 放弃防守后攻击方仍可继续追加合法攻牌。
- 确认收牌后桌面牌全部进入受攻方手牌。
- 受攻方空手且仍有未防住牌时进入等待中途添牌。

### 阶段 6：基础攻防收口

目标：在进入轮后结算前，补齐阶段 4 的 UI、测试和文档缺口。

任务：

- 已补齐 `ActionPanel` 中守牌移动/换位操作入口。
- 已补齐桌面牌位选择交互，支持来源牌位和目标牌位区分。
- 已明确 `ROUND_RESULT_READY` 只是结果待结算状态，不直接等同于轮完成。
- 已为阶段 4 关键动作补充测试。
- 已为复杂规则函数和核心状态流补充必要注释。

完成标准：

- 页面可以触发当前协议中已存在的攻防动作。
- 阶段 4 所有关键规则都有测试覆盖。
- `pnpm run lint`、`pnpm run typecheck` 和 `pnpm run test` 通过。

### 阶段 7：收牌、弃牌、添牌与轮转

目标：实现一轮结束后的完整状态推进，进入下一轮。

任务：

- 已采用服务端自动结算入口，不新增“进入下一轮”按钮或动作。
- 已实现受攻成功时，将桌面所有攻牌和守牌移入 `discardPile`。
- 已实现受攻失败时，将桌面所有攻牌和守牌移入受攻方手牌。
- 已实现结算后清空 `tablePairs`。
- 已实现按规则顺序为玩家补牌至最多 8 张。
- 已实现添牌顺序为主攻方优先，再从主攻方下家开始顺时针。
- 已处理牌堆不足和牌堆底部主牌被正常抽走的情况。
- 已根据本轮结果计算下轮主攻方、受攻方、助攻方和当前行动人。
- 已重置 `roundBattleState`，进入下一轮 `FIRST_ATTACK_READY`。

完成标准：

- 已实现一轮结果形成后自动进入下一轮。
- 已验证受攻成功和受攻失败的牌归属正确。
- 已验证添牌后总牌数仍为 54。
- 已实现下轮座位关系不写死 4 人。

测试重点：

- 受攻成功后桌面牌进入弃牌区。
- 受攻失败后桌面牌进入受攻方手牌。
- 添牌顺序严格符合规则。
- 玩家手牌已达到或超过 8 张时不添牌。
- 牌堆不足时只抽取剩余牌。
- 下轮主攻和受攻计算正确。

### 阶段 8：实际中途添牌

- 牌堆已空后的直接胜利、流局和全局排名边界留到阶段 10。

完成标准：

- 已实现常规中途添牌不再停在 `WAITING_DEFENSE_REFILL`。
- 已实现中途添牌后可以继续防守。
- 已验证中途添牌后牌数守恒。

测试重点：

- 受攻方中途添牌数量正确。
- 中途添牌不清空桌面牌位。
- 牌堆耗尽边界正确。
- 添牌后阶段切换正确。

### 阶段 9：主 3 换底与特殊规则

- 已实现换底不重新指定首攻方、受攻方、助攻方或当前行动方。

- 已补充特殊规则测试。

完成标准：

- 换底后玩家手牌和牌堆底牌正确。

### 阶段 10：牌堆耗尽与全局结算

完成标准：

测试重点：

### 阶段 11：机器人与单机可玩体验

目标：让 1 名真人可以和多个机器人完成一整局。

任务：

- 已为玩家模型和玩家视图增加机器人标识。
- 已新增独立机器人策略模块 `bot.ts`，不把策略逻辑塞入 `engine.ts`。
- 已实现最小机器人策略：
    - 有可换底牌时自动换底。
    - 首攻阶段出最小手牌。
    - 防守时出最小合法守牌。
    - 可加攻时出最小合法攻牌。
    - 无合法加攻时停止进攻。
    - 无合法防守时放弃防守。
    - 收牌阶段攻击方全部停攻后自动确认收牌。
- 已由核心提供机器人单步推进能力，前端按 0.5 秒延迟逐步请求机器人动作。
- 已在前端玩家面板展示机器人身份。
- 已在前端玩家面板展示机器人完整手牌，默认按一键排序规则排列，超出自身面板时横向滚动。
- 已把机器人每次自动动作选择写入对局事件，并保留原动作结果事件。
- 已调整机器人进攻策略：有合法加攻牌时立即加攻，只有全部攻牌被防住且自己无牌可加时才停止进攻。
- 已新增接口返回字段标记是否仍有机器人动作待推进。
- 已在只出不添阶段支持玩家或机器人出完牌后登记名次、收口当前轮，并跳过已完成玩家进入后续轮转。
- 暂未实现机器人难度等级、复杂换守牌策略和独立 AI 决策服务。

完成标准：

- 1 名真人 + 多名机器人可以基于当前规则推进对局。
- 机器人动作仍复用同一套核心动作校验，不绕过规则层。
- 机器人操作按单步接口推进，避免一次请求内长时间连续执行。
- 机器人不会提交非法动作。
- 机器人动作仍走统一规则入口。

测试重点：

- 机器人攻击、防守、加攻都合法。
- 机器人不会在非自己角色时行动。
- 机器人连续行动不会跳过真人回合。

## 6. 推荐开发顺序

当前建议顺序：

1. 阶段 1：统一文档基准。
2. 阶段 6：补齐基础攻防 UI 和测试。
3. 阶段 7：实现收牌、弃牌、添牌与轮转。
4. 阶段 8：实现实际中途添牌。
5. 阶段 9：实现主 3 换底。
6. 阶段 10：实现牌堆耗尽与全局结算。
7. 阶段 11：接入机器人。
8. 游戏界面阶段：对局内画面、交互、手牌、玩家形象和背景设计，详见 `docs/step/游戏界面step.md`。
9. 画面优化阶段：主页、个人页和移动端横屏收口，详见 `docs/step/画面优化step.md`。
10. 功能优化阶段：联机预留与代码收口，详见 `docs/step/功能优化step.md`。
11. 发布上线阶段：部署方式、分发渠道、发布流程和运营工作，详见 `docs/step/发布上线step.md`。

## 7. 测试策略

- 能测纯函数的地方优先测 `packages/game-core`，不要依赖页面。
- 协议字段变化必须同步检查 `packages/contracts`、`apps/server`、`apps/web`。
- 规则和状态机变更必须补回归测试。
- UI 交互变更至少要覆盖 loading、error、empty、success 的基本状态。
- 复杂流程优先用固定 seed 或构造状态，避免随机导致测试不稳定。

## 8. 常用命令

```bash
pnpm run format
pnpm run lint
pnpm run typecheck
pnpm run test
pnpm run build
```

使用建议：

- 改动单个文件时优先执行 `pnpm exec prettier --write <changed_files>`。
- 规则或协议变化后至少执行 `pnpm run typecheck` 和 `pnpm run test`。
- UI 或样式变化后至少执行 `pnpm run lint`，并在本地浏览器检查 PC 和移动横屏布局。
