# 攻花 H5 项目功能优化阶段步骤

## 1. 文档目标

- 本文档承接 `docs/step/开发阶段step.md` 后续工作，记录游戏逻辑、后端扩展、联机功能、机器人能力和工程质量优化。
- 当前核心单机规则闭环已在开发阶段文档中维护，本文档不重复描述开发阶段 1-11。
- 移动端横屏与页面体验收口已拆分到 `docs/step/画面优化step.md`。
- 发布上线、渠道和运营工作拆分到 `docs/step/发布上线step.md`。
- 后端数据库、账号、房间、快照和动作日志扩展详见 `docs/step/后端扩展step.md`。
- 后续开发仍默认遵守根目录 `AGENTS.md`，规则口径优先参考 `docs/rules.md`。

## 2. 推荐优化顺序

推荐先做游戏逻辑优化，再扩展后端和联机能力：

1. 阶段 1：游戏逻辑优化。
2. 阶段 2：后端扩展与数据持久化。
3. 阶段 3：联机功能开发。
4. 阶段 4：机器人性能分级。
5. 阶段 5：工程结构与质量优化。

选择原因：

- 当前项目的核心稳定性取决于 `game-core` 状态机，数据库、联机和机器人策略都依赖规则边界清晰。
- 先增加 `getLegalActions(gameState, playerId)`，可以让前端按钮、机器人和后续联机校验复用同一套动作能力。
- 后端扩展需要保存动作日志和快照，如果动作边界不清晰，后续持久化会放大调试成本。
- 机器人分级和 AI 机器人应建立在合法动作枚举之上，不能让机器人自己绕过核心规则。

## 3. 阶段 1：游戏逻辑优化

目标：提升规则完整度、状态机可维护性和异常局面的可诊断能力。

任务：

- 梳理 `engine.ts` 的动作处理、轮内推进、轮后结算、只出不添结算边界，按职责拆成更小模块。
- 增加合法动作枚举能力，例如 `getLegalActions(gameState, playerId)`，供前端按钮、机器人和未来联机校验共用。
- 增加逐玩家轮后补牌事件，替代仅显示总补牌数，方便观察机器人和真人补牌过程。
- 完善中途添牌后的边界规则：无法继续防守、牌堆耗尽、直接胜利和流局状态。
- 补充更多异常状态保护：重复卡牌归属、已完成玩家继续行动、桌面牌位非法引用、阶段与角色不一致。
- 优化事件结构，区分系统事件、玩家事件、机器人事件和错误事件，方便前端筛选展示。
- 建立规则变更清单，任何规则行为改动必须同步更新 `docs/rules.md` 和测试。

阶段内推荐拆分：

1. 先新增合法动作枚举，不改变现有动作提交行为。
2. 再把攻击、防守、轮内推进、轮后结算、换底和对局结束从 `engine.ts` 中逐步拆出。
3. 然后让前端操作按钮和机器人策略复用合法动作枚举。
4. 最后补齐异常状态保护和事件结构优化。

当前进度：

- 已新增 `packages/game-core/src/legalActions.ts`，提供核心合法动作枚举。
- 已让机器人策略和前端动作入口开始复用合法动作能力。
- 已新增 `packages/game-core/src/gameplay/` 目录，集中收纳同属游戏流程的拆分模块，避免核心目录文件过散。
- 已新增 `packages/game-core/src/gameplay/roundSettlement.ts`，承接轮结算、轮后补牌、只出不添排名和下一轮角色计算。
- 已新增 `packages/game-core/src/gameplay/defenseActions.ts`，承接出守牌、撤回守牌、移动守牌、放弃防守和确认收牌。
- 已新增 `packages/game-core/src/gameplay/attackActions.ts`，承接首攻、追加攻牌和停止进攻。
- 已新增 `packages/game-core/src/gameplay/gameProgress.ts`，承接动作成功后的轮内推进、受攻成功判断、中途添牌和守恒校验。
- 已新增 `packages/game-core/src/gameplay/gameSetup.ts`，承接洗牌、发牌、翻主牌和首攻角色初始化。
- 已新增 `packages/game-core/src/gameplay/trumpExchange.ts` 和 `packages/game-core/src/gameplay/trumpRules.ts`，承接换底动作与主牌换底规则。
- 已新增 `packages/game-core/src/gameplay/botStep.ts`，承接机器人单步推进入口，机器人策略仍保留在 `bot.ts`。
- 已新增 `packages/game-core/src/gameplay/actionPhase.ts`，承接动作阶段校验。
- 已将 `packages/game-core/src/engine.ts` 收口为对外状态机入口，主要负责动作分发和稳定导出。

完成标准：

- 核心状态机模块职责清晰，单个文件不会继续无限增长。
- 前端和机器人可以复用合法动作枚举，不再各自推断过多动作条件。
- 关键规则边界都有测试，新增规则不依赖手动体验验证。

测试重点：

- 每类动作都有合法和非法测试。
- 只出不添、直接胜利、流局、排名和下一轮角色计算覆盖完整。
- 合法动作枚举结果与实际 `applyGameAction` 校验一致。

## 4. 阶段 2：后端扩展与数据持久化

目标：让对局、用户和配置具备长期保存能力，为联机和运营做准备。

任务：

- 按 `docs/step/后端扩展step.md` 接入 `PostgreSQL + Prisma`。
- 把当前内存 `gameStore` 抽象为仓库接口，先保留内存实现，再增加数据库实现。
- 增加动作日志仓库，所有玩家、机器人和系统动作都能持久化。
- 增加对局快照保存和恢复能力。
- 增加用户昵称、头像、个人配置、自动排序配置和机器人偏好配置。
- 增加房间、对局记录、对局结果和战绩统计。
- 增加数据清理策略，避免测试对局和过期房间无限累积。

完成标准：

- 服务重启后重要对局或用户配置不会丢失。
- 内存仓库和数据库仓库可以通过配置切换。
- 用户基础配置能被前端读取和保存。
- 动作日志和对局快照可用于排查问题和恢复未结束对局。

测试重点：

- 仓库接口内存实现和数据库实现行为一致。
- 对局快照序列化、反序列化后仍能继续动作。
- 用户配置保存后刷新页面仍能恢复。

## 5. 阶段 3：联机功能开发

目标：在现有单机权威后端基础上接入多人房间和实时同步。

任务：

- 确保所有玩家动作都是可序列化协议。
- 确保服务端状态可以快照化。
- 清理页面中对玩家身份、座位和动作权限的硬编码。
- 明确后续 WebSocket 或轮询同步的数据边界。
- 补充模块文档和可复用能力索引。
- 为后续机器人 AI 化预留策略接口，不让 AI 直接绕过 `game-core` 规则校验。
- 增加房间模型：房间号、玩家列表、座位、房主、准备状态、机器人填充策略。
- 增加玩家身份模型：访客、本地昵称、登录用户、断线重连标识。
- 增加联机接口：创建房间、加入房间、离开房间、准备、开始对局、提交动作、获取房间快照。
- 增加实时同步通道，优先考虑 WebSocket；如果部署渠道受限，可先使用轮询作为降级方案。
- 增加动作序号和状态版本号，防止重复提交、乱序提交和旧快照覆盖新状态。
- 增加断线重连和超时托管：玩家短暂断线后保留座位，超时后可由机器人托管。
- 增加房间内事件广播，保证所有客户端看到一致的事件顺序。

完成标准：

- 未来接 WebSocket 时，前端只需要替换同步方式，不需要重写规则。
- 动作校验仍由后端和 `game-core` 负责。
- 单机机器人、未来 AI 机器人和真人联机动作都能复用同一套动作协议。
- 多个真人玩家可以在同一房间内看到一致对局状态。
- 断线重连后能恢复到当前玩家视角。
- 非当前玩家不能代替他人提交动作。

测试重点：

- 玩家动作 DTO 不依赖本地 UI 状态。
- 服务端对局状态可以序列化和恢复。
- 前端切换同步方式后，动作提交和玩家视角消费边界保持稳定。
- 已完成玩家、机器人玩家和真人玩家在轮转中的身份边界清晰。
- 房间创建、加入、离开、准备和开始对局流程正确。
- 动作重复提交、乱序提交和断线重连不会破坏权威状态。

## 6. 阶段 4：机器人性能分级

目标：在当前规则机器人基础上增加不同强度策略，让单机对局更接近真实玩家体验。

任务：

- 抽象 `BotStrategy` 策略接口，规则机器人、增强机器人和未来 AI 机器人都通过同一入口选择动作。
- 把当前 `bot.ts` 拆成策略入口、合法动作枚举、评分器和默认规则策略，避免单文件继续膨胀。
- 增加机器人等级配置：
    - 简单：优先出最小合法牌，弱化换守牌和保留关键牌能力。
    - 普通：按当前策略执行，能防守、能加攻、能停止进攻。
    - 困难：考虑保留主牌、优先消耗低价值牌、根据受攻方剩余手牌控制加攻节奏。
    - 实验 AI：通过后端 AI 服务选择动作，但必须经过 `game-core` 二次校验。
- 增加机器人策略配置来源，先支持创建对局参数或服务端默认配置，后续接个人页配置。
- 机器人动作失败时必须回退到默认规则策略，并输出中文日志和事件。
- 增加机器人策略单元测试，覆盖各等级在相同局面下的差异行为。

完成标准：

- 不同机器人等级可以在同一局中共存。
- 机器人策略不直接修改 `GameState`，只返回动作。
- 所有机器人动作仍通过 `applyGameAction` 或等价核心入口校验。
- AI 策略关闭时不影响当前单机对局稳定性。

测试重点：

- 简单、普通、困难策略在固定局面下返回预期动作。
- 非法 AI 输出会被拒绝并回退规则策略。
- 机器人出完牌、停攻、收牌和下一轮轮转不会卡住。

## 7. 阶段 5：工程结构与质量优化

目标：降低后续功能迭代成本，提高可测试性和可维护性。

任务：

- 根据当前拆分继续收口 `packages/contracts`，保持主协议、接口协议、日志协议分离。
- 给 `apps/web/src/pages/gamePage.tsx` 拆分页面布局、拖拽处理、机器人推进、手牌排序等 hooks 或子组件。
- 给 `apps/server/src/gameStore.ts` 拆分房间仓库、对局仓库和机器人推进服务。
- 增加接口层测试，覆盖创建对局、提交动作、机器人单步推进和对局不存在返回。
- 增加前端组件测试或 Playwright 冒烟测试，覆盖创建对局、出牌、防守、机器人推进。
- 建立 CI 检查：格式化、lint、typecheck、test、build。
- 建立错误码和事件码清单文档，避免新增功能时重复或误用枚举。

完成标准：

- 页面、服务端和核心规则模块边界更稳定。
- 新增功能时可以快速定位修改位置。
- 关键流程能通过自动化检查提前发现回归。

测试重点：

- `pnpm run lint`、`pnpm run typecheck`、`pnpm run test`、`pnpm run build` 在 CI 中稳定通过。
- 页面拆分后现有操作行为不变。
- 服务端拆分后接口响应结构不变。
